## 1. 验收结论

当前系统“核心服务可启动、核心查询链路大体可用、自动化测试通过”，但不建议直接按完整生产验收通过。主要原因是数据口径、数据库表结构和调度运行存在几个会影响日常使用的硬问题：

1. 数据质量总门禁为 `FAIL`，公告、分析推荐、复盘、快照、分钟线覆盖存在明显缺口。
2. 数据库 DDL 与代码不一致，导致每日复盘写入失败、模拟交易自动化状态接口内部报错。
3. API 启动会自动拉起嵌入式调度器和 QMT 运行时，验收期间实际触发了多次后台任务，存在“打开页面就改数据/跑任务”的运维风险。
4. 多个重接口在 8-10 秒内不能稳定返回，影响页面体验。
5. 前端桌面主流程基本能看，但存在加载态残留、日期口径混乱、移动端不可用等体验问题。

建议验收等级：有条件通过“开发/自用研究环境”验收；暂不通过“稳定生产/自动化盘中工作台”验收。

## 5. 数据库表结构问题

### 5.1 `st_sim_event` 缺少 `short_name`

接口：`GET /api/sim-trade/automation-status`

对外状态码：200  
实际返回：

```json
{
  "sim_auto_ready": false,
  "sim_auto_status": "error",
  "sim_auto_label": "模拟自动交易状态异常",
  "error": "Unknown column 'short_name' in 'field list'"
}
```

代码位置：

```text
server/api/routers/sim_trade.py
SELECT event_time, event_type, stock_code, short_name, strategy_type, message
FROM st_sim_event
```

当前表结构：

```text
st_sim_event:
id, trade_mode, event_date, event_time, event_type, signal_id, order_id,
position_id, stock_code, strategy_type, severity, message, payload, created_at
```

影响：

- 模拟交易页面展示“模拟自动交易状态异常”。
- 自动交易状态无法可信展示。
- 代码用 200 包裹错误，监控层不容易发现。

建议：

- 方案 A：给 `st_sim_event` 增加 `short_name varchar(128)` 并补历史数据。
- 方案 B：查询时从 `si_all_code` 左连接名称，避免事件表冗余列。
- 同时增加真实库表 schema 测试，覆盖该接口。

## 13. 总体判断

ProBigA 的核心能力已经成形：数据采集、行情热点、资金流、推荐、自选、模拟交易、调度管理和页面工作台都有可运行版本；现有测试集也比较完整，说明代码层基础不错。

但本次验收的主要问题不在“能不能跑”，而在“跑出来的数据是否一致、自动化是否可靠、页面是否能让人一眼判断当前数据是否可信”。在股票研究系统里，日期口径、快照新鲜度、调度单实例、推荐/复盘链路比普通页面展示更关键。建议先按 P0/P1 修复后再做第二轮验收。
