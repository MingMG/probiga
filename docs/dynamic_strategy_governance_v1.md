# 动态策略治理与竞技场 V1

## 1. 文档定位

本文档是动态策略治理模块的生产行为契约。实现、页面、调度、健康检查和生产验收必须使用同一套口径；任何未满足本契约的结果都不得解释为“治理成功”或“可交易”。

本模块只用于研究验证、策略比较和模拟资金治理：

- 策略数量不设固定上限，也不以当前清单作为允许名单。清单策略只是初始库存，运行时可以注册新的策略和新版本。
- 排名、通过门槛或获得模拟权重都不代表未来一定盈利，也不构成收益承诺、投资建议或真实交易指令。
- 模块没有真实下单权限。所有响应、快照和分配记录的真实下单权限必须固定为关闭，且不得调用实盘下单链路。
- 数据缺失、陈旧、未经确认、计算失败、写入失败或没有合格策略时一律失败关闭：不新增风险敞口，当前轮模拟资金保持 100% 现金。

## 2. 策略与版本身份

### 2.1 动态注册

`strategy_key` 是策略家族的稳定标识，不限制为当前内置策略。每个可评估对象必须具有独立版本；策略的真实身份至少由以下内容共同确定：

- `strategy_key`
- `strategy_version`
- 规范化后的配置内容及其 `version_hash`
- 评估器类型、评估器配置、参数、最大持有期和成本模型版本
- 冻结的市场路由策略版本、市场状态配置版本及配置哈希、四种市场状态的适配系数

策略名称、分类和说明是展示信息，不能代替版本身份。运行、指标、生命周期、排名、票池、模拟分配和审计都必须绑定到上述精确版本，禁止只按 `strategy_key` 混用证据。

### 2.2 版本不可覆盖

- 已存在的 `(strategy_key, version)` 不可覆盖、回滚或借注册动作复活。
- 完全相同的重复请求只能作为幂等成功处理，不得重置生命周期、所有者、说明或当前版本；内容不同必须拒绝并要求新版本号。
- 新版本必须生成新的不可变版本记录，并从“影子观察”重新开始；不得继承旧版本的资金资格或把旧版本前向收益当作新版本证据。
- “已淘汰”是版本终态。恢复研究只能注册真正的新版本，不能重新提交原版本。
- 淘汰动作同时关闭治理注册表和旧策略中心适配器中的该策略；后续启停接口不得重新启用已淘汰版本。普通停用版本重新启用时也只能回到“影子观察”，不能直接取得资金资格。
- 初始清单播种只负责补齐缺失记录，不得在服务重启或多进程启动时把已注册的新版本回滚为清单旧版本。
- 股票清单策略使用 `manifest_version:strategy_key` 作为精确版本；V3 策略袖套使用 `model_version:primary_strategy_key`。V3 已执行模拟证据必须在完成的决策运行、主预测、成交意图、买入订单、买入 fill、现金链、前向账本和治理注册表之间保持精确关系。部署迁移只为可由这些事实逐项证明的旧记录回填版本；无法唯一证明的空版本记录保留为隔离历史，不能参与治理。非空但关系无效的记录属于生产验收失败，不能静默跳过。

### 2.3 组合版本

组合的真实身份由 `combination_key`、组合版本、配置哈希和成员清单共同确定。成员必须绑定精确的策略版本和规范化权重；任一成员版本、权重、约束或成本口径变化都必须产生新的组合版本。

组合不能只依赖成员分数或成员收益指标的加权平均取得资格。除成员均满足要求外，还必须冻结成员版本、权重、检查点身份和成员日频事实集合哈希，在窗口起点按权重建立复算配方，之后让成员权重随各自净值自然漂移；禁止假设每日无成本再平衡。组合据此从成员已验证事实链重建逐日虚拟净值，独立计算扣费后收益、回撤和每日收益序列，并具有该组合版本自己的 Walk-Forward 版本选择验证。系统不为组合伪造独立现金 CNY 或组合日频资金事实；组合健康快照只保存门槛摘要、配方哈希和成员事实集合引用。若未来引入再平衡，必须注册新组合版本，冻结频率/阈值并扣除实际换仓成本。组合的版本化约束至少包括成员最大权重、最大成对相关性、相关性最少共同观测数、最大股票重合度和最大行业集中度；缺少任一约束所需的底层数据都应失败关闭。组合与其任一成员不得在同一资金分配中重复获得资金，避免形成未披露的重复敞口。

### 2.4 动态执行适配器可信根

数据库中的适配器名称、版本和制品 SHA 都只是声明，不能让任意 Python 对象取得执行权。部署端只接受可信发布根内、路径不含符号链接、由模块同名导出的具名 `types.FunctionType` 模块级纯函数；实例可调用对象、绑定方法、lambda、嵌套函数、闭包、默认参数、运行期导入、全局写入、非白名单 builtin、模块对象以及可变或不透明全局一律拒绝。制品指纹必须同时绑定适配器模块相对路径与文件 SHA-256、实际引用的项目模块文件 SHA-256、生产依赖锁 SHA-256、发布树 SHA-256 和 Python ABI。生产进程只有在可信启动清单提供预期 registry seal SHA-256 并显式封印后才可执行；未封印时能力页面和执行路径都失败关闭。

每次动态候选运行把稳定的权威输入/输出与随机审计身份分开：`input_hash`、`output_hash` 和 `stable_result_hash` 不包含 `run_uid`、`completed_at` 或回执哈希；相同策略版本、绑定、交易日、输入和候选结果重复运行时，治理输入哈希和决定哈希必须相同。随机运行号、完成时间和回执哈希写入独立仅追加 `st_strategy_adapter_run_receipt`，零候选的完整运行同样留痕。

动态影子执行链已经落为四张严格结构表：候选事实、影子试验计划、完整试验链和退出成交绑定。只有生命周期为“影子观察”、动作明确为买入且候选状态可执行的对象才能建立计划；计划再接入既有 V2 内部模拟 intent/risk/order/fill 与 V3 成交后前向证据，必须由数据库外键、逐层事实哈希、实际费用、现金事件和退出分配共同证明，调用方自造的自洽哈希链仍一律拒绝。就绪状态区分为“已验证但暂无试验”“已验证、试验尚未成熟”“已验证且证据成熟”“证据无效”四类；只有完整成熟链可以把 `funding_pipeline_ready` 置为 `true`，但这仍只是治理模拟资金准入条件。所有表级约束和输出的自动真实下单、真实下单权限永久固定为关闭。

## 3. 中文生命周期

页面只展示中文状态；内部代码仅用于接口兼容和审计。

| 内部代码 | 页面名称 | 行为与模拟资金资格 |
|---|---|---|
| `ACTIVE` | 正常运行 | 精确版本的已确认证据通过全部硬门槛后，才可参与模拟资金分配 |
| `REDUCE` | 降权运行 | 仍通过全部硬门槛，但健康度或稳定性下降；竞争得到的基础预算固定乘 0.50，折扣资金留在现金且不转分给其他策略 |
| `SHADOW` | 影子观察 | 新策略、新版本或恢复后的版本；只积累证据，不获得模拟资金 |
| `SUSPENDED` | 暂停使用 | 暂停模拟资金资格；满足恢复条件后也必须先返回影子观察 |
| `RETIRED` | 已淘汰 | 当前版本终态，不可恢复；只能注册新版本重新验证 |

生命周期约束：

- 人工操作可以暂停、转回影子研究或淘汰，必须填写具体中文理由；但已经“暂停使用”的版本不能由人工直接恢复。
- 人工操作不能直接授予“正常运行”或“降权运行”。这两个状态只能由每日治理基于已确认、足够新鲜且绑定精确版本的证据自动授予。
- `SUSPENDED` 不能在同一轮直接跳到 `ACTIVE` 或 `REDUCE`。只有严格晚于暂停证据高水位的新证据达到初步恢复门槛时，每日治理才可把它恢复到 `SHADOW`；暂停前的连续通过次数全部作废，之后再重新累计完整确认。
- `enabled=false` 和 `RETIRED` 版本绝不执行、绝不计入动态候选完成 quorum、绝不进入任一股票池或资金候选；`SUSPENDED` 只允许独立诊断展示，不进入 quorum、股票池或分配。每一层都必须重新校验，不能信任上游自报的 `paper_allocation_eligible=true`。
- 自动升级、降权、暂停和恢复都必须记录门槛结果、证据哈希、目标交易日、运行编号及中文理由。
- 排名和健康分不能覆盖任何盈利硬门槛，也不能改变人工不可直接授资的限制。

## 4. 证据与盈利硬门槛

### 4.1 证据原则

资金资格的收益事实只接受版本冻结之后产生的内部模拟成交与内部逐日组合账本。回测和外部验证产物可用于研究、参数选择以及检查客户端所声明的版本选择过程是否遵守样本外时序隔离，但不能证明其来源权威，也不能冒充资金收益、真实费用或组合回撤。Walk-Forward 必须按时间顺序切分，并执行与标签期限和最大持有期相匹配的 purge/embargo，避免未来数据泄漏、重叠标签、重复样本和参数回看。

20/60/120 的“日”固定指权威交易日，不是 `N×2` 个日历日近似。系统从交易日历取截止日向前精确 N 个已收盘会话，并要求每个会话的未复权日线都能连接 `QMT_DAILY_UNADJUSTED_PRECLOSE_V2` 逐行认证：来源必须为 `gj_big_qmt_inner`，`pre_close` 必须直接来自 QMT 原生 `preClose` 且标记为 `NATIVE_QMT`，源数据版本及 OHLCV、成交额、前收盘价快照必须与当前规范日线逐字段一致。旧批次认证、由上一日收盘价推导的 `pre_close`、未标明来源的历史行或任一快照漂移均不能通过。窗口起止日、会话数、逐日认证摘要、协议版本及 SHA-256 必须进入证据。认证缺日时整轮持久化治理阻断，不得把数据中断解释为策略失效。

QMT 生产采集和历史补数固定使用不复权 BigQMT 路由。生产端 producer 在缺少原生 `preClose` 时必须写入 `MISSING_NATIVE_QMT`，不得回退到 `previous_close`；本地历史表旧行升级后先标记 `UNVERIFIED_LEGACY`，只有重新由 BigQMT 抓取并完成逐行认证后才能用于治理。逐行认证记录仅追加且由数据库触发器禁止更新或删除；源数据修订产生新版本和新认证，旧认证保留但不能匹配当前行。

每份内部资金证据至少记录：

- 精确策略或组合版本及其配置哈希
- 原始观察或逐笔结果的权威来源回执、数据日期、生成时间和成本口径
- 20/60/120 日窗口、样本数量、覆盖天数和结果哈希
- 提交者、确认者或自动证明来源，以及确认时间

外部验证产物固定使用 `probiga.strategy-validation-artifact.v3`，用途只能是 `VERSION_SELECTION_ONLY`。它可以作为淘汰参数、比较版本和检查时序隔离的客户端研究声明，但无论结果多好都没有 `funding_authority`，不能直接或间接生成模拟资金资格，也不能替代内部日频 NAV、实际费用、真实持仓重叠、现金约束和每日盯市事实。当前 v3 没有绑定可由服务器从 QMT/数据库逐行重放的权威 source receipt；字段 `source_dataset_hash` 只是客户端提交内容的规范哈希，不是权威源数据认证。即使不同账号完成复核，也只证明结构、时序和哈希内部自洽，不证明这些收益真实发生。页面和接口必须固定展示 `CLIENT_DECLARED_UNATTESTED`、`STRUCTURE_AND_REPRODUCIBILITY_ONLY`、`funding_authority=false` 和 `real_order_authority=false`，不得把它称为权威、独立来源实证或资金证据。产物仍必须包含逐笔样本外净收益、每笔验证成本、入场交易日、标签实际成熟时间、观测高水位、由逐笔收益顺序复利重建的诊断曲线、五段以上 Walk-Forward 分段、提交内容 SHA-256、聚合指标 SHA-256 和完整产物 SHA-256。标签成熟日必须属于绑定的权威交易日窗口，距离入场日不得短于版本冻结的标签期限、不得长于最大持有期，并且在证据高水位和截止日前已声明成熟；因此窗口尾部尚未知晓的未来收益不能进入样本。外部曲线的 `drawdown_basis` 只能是 `sequential_trade_compounded_equity`，不能声称它是考虑重叠持仓、现金和逐日盯市的组合净值。服务端从提交的逐笔样本和诊断曲线重新计算交易数、覆盖天数、胜率、平均盈亏、盈亏比、净期望、利润因子、诊断回撤、成本压力、分段结果和头部盈利贡献；客户端自报值只要与重算值不一致就拒绝，但重算不提升来源权威性。

v3 产物必须携带完整的 `validation_protocol`：`label_horizon_days`、与不可变版本一致的 `max_holding_days`、`purge_days` 和 `embargo_days`。`purge_days` 不得小于标签期限与最大持有期二者中的较大值，`embargo_days` 不得小于标签期限。每个分段都必须携带可逐项重算的训练样本以及训练集、测试集哈希；训练样本的固定字段为全局规范 `observation_id`、`observed_at`、`label_available_at`、特征快照哈希和标签快照哈希。其中 `observed_at` 固定表示预测时可见的特征/入场观测时间，不是事后标签写入时间；`label_available_at` 表示该样本标签实际成熟时间，两者必须位于权威交易日且满足 `observed_at <= label_available_at <= train_end` 数据高水位，实际成熟交易日距离还必须落在冻结的标签期限与最大持有期之间。训练结束与测试开始之间按权威交易日历满足 purge。样本外测试段可以连续，但必须严格按时间排序、不得重叠，而且底层每一笔样本必须且只能归属一个测试段。后续训练一旦消费既往测试区间或其全局规范样本编号，embargo 的计时起点必须是该测试段全部测试样本的最大 `label_available_at`，不得错误地从 `test_end` 起算；实际标签全部成熟后还必须经过完整的 `embargo_days` 权威交易日，少一个交易日也拒绝。训练与测试样本编号均为全局 64 位 SHA-256 规范编号；同一编号绑定不同事实、或相同训练事实使用不同编号别名都会失败关闭。所有测试段只能覆盖版本冻结后的精确交易日窗口，训练集和测试集哈希必须由规范化后的精确样本重算，禁止重用、遗漏、换日期或重新包装制造独立性。

客户端提交的任意聚合字典不能成为授资依据。新增外部声明的来源固定为 `EXTERNAL_SUBMITTED`，先进入“等待结构复核”；只有完成类型、固定字段、范围、当前版本、版本冻结时间、20/60/120 日窗口、日期、高水位、purge/embargo、重复样本集和全部哈希校验，并由不同认证账号复核后，才可标记为“结构已确认”。即使已确认，外部声明仍只用于研究版本选择，不能提供授资所需的收益、费用或回撤事实；未确认或被拒绝的声明仅保留审计。未来若增加权威 source receipt，必须启用新协议版本并从服务器按 QMT/数据库事实逐行重算，不能把已有 v3 声明原地升级成已认证证据。

授资口径只接受一个不可替代的权威来源：精确版本绑定的内部资金事实链。外部 v3 声明既不是必要条件，也不能增强、削弱或否定内部资金资格：

1. `INTERNAL_PORTFOLIO_CHECKPOINT_FACT_LEDGER_V3`：从内部已执行模拟成交、实际费用、现金变动、重叠持仓和每日未复权收盘价重建逐日净值。资金账户的 `policy_hash` 必须逐字节等于当前权威 `strategies/portfolio_policy_v2.json` 的 `config_hash`，并同时绑定该政策声明的 `policy_version`、`fee_profile_version` 和 `instrument_rule_version`；V3 冻结账户的佣金、最低佣金、过户费、卖出印花税和默认滑点必须与该 V2 政策及既有 A 股 paper fee profile 完全一致，启动校验不一致就停止授资。每笔买卖必须连接唯一 raw fill、订单、完整现金事件绑定和仅追加执行证据，且现金事件引用的执行证据必须精确绑定同一 `fee_profile_version`、A 股全部六个费率字段与 `other_fee_json`、规范 `fee_schedule_json` 的 `fee_schedule_hash`、当前权威 `instrument_rule_version`与规范 `instrument_rule_json/hash`，以及规范 `accounting_request_json` 和 `settlement_evidence_json` 中对同一费用/器械规则哈希的引用；数量、金额、费用、时点均可重算。旧证据缺少任一费用字段、哈希或现金引用时只能标记为待重建/不授资，不允许根据当前费率回填、伪造或宽松兼容。每个 raw SELL fill 必须通过 `st_forward_exit_allocation_v3`，按 `(filled_at, fill_id)` 确定性顺序逐账户、逐证券消费此前 raw BUY fill 的 FIFO 剩余量；同一 SELL 的 `allocation_sequence` 必须连续为 `0..N-1`，每个退出/入场 fill 对只能有一行。具有合法 V3 主归因的已消费 BUY lot 写为 `ATTRIBUTED`，非 V3 或无法归因但确实被 FIFO 消费的 BUY lot 写为 `UNATTRIBUTED`，不得丢弃；若 BUY 库存不能完整覆盖 SELL，则整次同步失败并回滚。每笔分配的金额和费用按 6 位精度计算，最后一个 FIFO 分配吸收 raw 总额减去前序合计的精确尾差；数量、金额和费用必须与整笔 SELL 精确相等，不使用容差。任一卖出 fill 的分配数量、金额、费用、序号、费用策略或现金绑定不全局守恒，或者出现跨交易日聚合、重复现金事件，相关策略资金证据立即隔离且生产健康检查失败。持仓估值只接受 QMT v2 逐行认证日线，缺日线不能假装停牌沿用旧价；`pre_close` 与上一未复权收盘价偏差超过 0.05% 视为公司行动/价格断点，在公司行动现金与数量账本上线前整段失败关闭。账本产出哈希、扣费后交易收益、实际费用、最大回撤和每日收益序列；窗口首日回撤必须以上一权威交易日权益为开盘基线，不能漏掉首日亏损。其回撤口径固定为 `internal_version_bound_portfolio_equity`，成本口径固定为 `actual_ledger_fees`。

V3 把最近 120 个权威交易日写成单份、仅追加的规范日频事实链；检查点只保存资金边界、未平持仓、权威账户事实哈希、费用/执行政策指纹、事实链精确成员集合哈希和前序检查点链，不重复内联 20/60/120 三套窗口数组。每个首次出现的精确版本/账户只允许一次精确全历史 `FULL_BOOTSTRAP`；同一治理轮可以批量引导多个新版本，之后只能从已验真的规范检查点做不超过 370 个会话的 `BOUNDED_INCREMENTAL` 重放。旧的 `INTERNAL_PORTFOLIO_LEDGER_V1` 与 `INTERNAL_PORTFOLIO_CHECKPOINT_LEDGER_V2` 只允许历史展示，不能通过当前授资门槛。

检查点持久化还有固定容量合同：单检查点目标平均不超过 8 KiB，检查点与本轮新事实合计目标不超过 8 MiB、硬上限 16 MiB；批量写入每批最多 100 行且不超过 4 MiB；canonical 资金清单不超过 1 MiB，共享审计锚不超过 128 KiB。首次引导另受明确的每轮资源预算约束：默认最多引导 8 个新版本、最多 120 秒、首次引导检查点合计最多 4 MiB；条数可通过 `PROBIGA_FUNDING_BOOTSTRAP_MAX_STRATEGIES_PER_RUN` 配置但安全上限为 25，时间和字节分别通过对应环境项配置并受硬上限约束。达到条数、时间或字节预算时，剩余版本必须分别记录 `CHECKPOINT_BOOTSTRAP_COUNT_BUDGET_DEFERRED`、`CHECKPOINT_BOOTSTRAP_TIME_BUDGET_DEFERRED` 或 `CHECKPOINT_BOOTSTRAP_BYTE_BUDGET_DEFERRED`，保持零模拟资金并在后续治理轮按确定顺序继续；注册表和策略总数不设固定上限。超过目标值必须在健康页显式告警，超过任一硬上限则整轮失败关闭，禁止截断策略集合、事实链或审计字段来“通过”验收。

canonical 资金清单使用 `probiga.strategy-funding-checkpoint-manifest.v2` 的紧凑三根结构，不内联全部策略记录：`checkpoint_root` 精确锚定有独立内部 NAV 的策略检查点，`combination_recipe_root` 精确锚定由成员检查点重建的组合配方，`ineligible_root` 精确锚定本轮不可授资实体及理由。每个根只保存数量、集合哈希和不超过 100 行一批的批次首尾/批次哈希；共享审计同时绑定 coverage 和三个根。健康检查必须独立重建三根、复算每批及总根哈希，并证明“策略检查点 + 组合配方 + 不可授资”互斥且精确覆盖当前版本实体集合；组合配方计入资金就绪覆盖，但不计入策略检查点数量，也不得产生组合现金事实。策略和组合的业务数量不设固定上限；运行健康门按当轮 canonical 实体数动态计算预期事实数，并以“预期数量 + 1”查询证明数据库没有被截断。资源保护由每批最多 100 个实体、单检查点最多 370 条日频事实、8 MiB 目标清单、16 MiB 硬上限、平均检查点最多 8 KiB、总字节和执行期限共同约束；任何容量或覆盖越界都失败关闭，不得静默截断或漏检。

两张资金表的 `account_id` 都有冻结的显式索引，但刻意不向既有 `st_trade_account_v2` 建外键：生产父表沿用 MySQL 8.4 默认 `utf8mb4_0900_ai_ci`，资金合同固定为 `utf8mb4_unicode_ci`，字符列排序规则不一致会在全新 MySQL 上以 errno 150 拒绝建表。这个兼容选择不授予账户权威；每次读取都必须重新确认唯一内部模拟账户、canonical 账户绑定和完整账户事实哈希，任一账户歧义、状态变化或哈希不一致都使该检查点失效。未来只有在受控迁移窗统一父子列字符合同并完成历史重验后，才能新增账户外键。
内部资金事实链缺失、过期、版本不一致、覆盖不足或任一哈希无效时，该策略或组合只能继续研究或影子观察，不得取得模拟资金。外部 v3 声明缺失不会阻断一份已经完整通过内部资金门的版本；外部 v3 声明即使表现优秀也只能帮助决定是否让挑战者进入无资金影子观察，后续仍须从零积累内部事实。策略组合必须按冻结配方从全部成员的已验证日频事实链复算逐日虚拟净值；不得把成员聚合指标加权后伪装成组合账本，也不得伪造组合现金事实。

### 4.2 新鲜度与目标日期

- 当前轮治理只能使用不晚于目标交易日、且满足生产新鲜度策略的证据。
- 行情、候选快照、市场状态或新增验证证据为 `missing`、`degraded`、`stale`、`unverified`、`pending` 时，不得自动升级，不得进入模拟可交易池，模拟资金保持现金。
- 观察池可以保留陈旧记录用于历史复核，但必须清楚显示数据日期和“不可用于当前决策”的原因。
- 历史回放或回填只能生成历史快照，不得修改当前生命周期；当前生命周期变更只允许针对最新已确认交易日执行。

### 4.3 多窗口门槛

系统同时计算 20、60、120 日窗口。60 日是主要准入窗口；20 日用于发现近期衰减和恢复迹象；120 日用于验证长期稳定性。任何关键窗口缺失、明显恶化或相互矛盾时，不得用单一高分覆盖风险。

所有资金窗口共同强制版本绑定、内部版本组合账本、实际成交费用、仅追加执行证据、精确权威会话窗口和新鲜度；其中任一项不成立就失败关闭。盈利、盈亏比、利润因子、费用和回撤均以内部组合账本为准。外部 Walk-Forward 只是一条来源未认证的研究声明，单独留榜且不参与资金门。

| 窗口 | 样本与覆盖 | 经济门槛 |
|---|---|---|
| 20 日衰减门槛 | 内部成熟交易不少于 20 笔；内部组合净值覆盖不少于 20 个权威交易日；精确会话数必须等于 20 | 扣除真实费用后的日均净收益严格大于 0；日频利润因子严格大于 1.00；`日均毛收益 - 1.5 × 内部账本实际日均成本` 按生成端四位小数口径重算后必须与记录值完全一致且严格大于 0 |
| 60 日资金准入门槛 | 内部成熟交易不少于 80 笔；内部组合净值覆盖不少于 60 个权威交易日；精确会话数必须等于 60 | 日均净收益严格大于 0，且日均毛收益至少覆盖 3 倍日均成本；日频盈亏比不低于 1.10；日频利润因子不低于 1.30；最大回撤不超过 12%；1.5 倍成本压力仍为正；最佳 5 个盈利日贡献不超过 70% |
| 120 日长期稳定门槛 | 与 60 日资金准入使用相同的最低内部交易数和组合净值覆盖要求；精确会话数必须等于 120 | 与 60 日资金准入使用相同的经济门槛 |

资金口径中的 `win_rate_pct` 是内部资本加权日频 NAV 的盈利日占比，`net_expectancy_pct` 是日均净收益，`payoff_ratio` 是盈利日与亏损日平均幅度之比，`profit_factor` 是盈利日收益总和与亏损日收益绝对值总和之比，`top5_profit_contribution_pct` 是最佳 5 个盈利日对总盈利的贡献；它们都不是逐笔交易统计。逐笔胜率、逐笔盈亏比和逐笔头部贡献只出现在 `trade_episode_diagnostics` 或独立信号研究口径，不能替代资金准入指标。

只有 `strategy-governance-decision.v7` 具有当前模拟资金语义；v6 及更早决策仅用于历史展示。v7 必须从内部资本加权日频 NAV 按时间顺序切成 5 个互不重叠的段，至少 4 段日均净收益严格为正；这里不是外部 Walk-Forward 分段，也不得用外部逐笔样本替代。三个窗口都必须对日频净收益采用 HAC/Newey-West 相关性稳健估计，并以单侧 95% 置信下界判断净期望、利润因子和盈亏比，而不是用点估计过门。20/60/120 日窗口的最小有效样本量（ESS）分别为 10/30/60；ESS 不足时即使名义交易日或交易笔数足够也不授资。

v7 还必须在服务端固定、不可由调用方缩减的“对象 × 窗口”检验族上执行 Benjamini-Yekutieli FDR，`q=0.05`。检验族同时覆盖策略与组合、20/60/120 日、当前与历史版本以及已淘汰、失败和挑战者对象；缺失或无法计算的检验按 `p=1` 处理，禁止删除失败对象来提高通过率。只有内部五段门、HAC/ESS/单侧 95% 下界和 BY-FDR 全部通过，且前述经济、数据、执行、路由与证据门禁均通过，v7 才能给出模拟资金资格。20 日只承担近期衰减确认，不放宽共同证据条件，也不能单独授予资金；策略和组合均调用同一个规范窗口门槛，不允许组合使用另一套手写捷径。

自动进入“正常运行”或“降权运行”还要求 3 次相互独立、按权威交易日隔开的确认。相邻确认的最小间隔为 `max(最大持有期, 标签期限, 5)` 个权威交易日；同一证据高水位、同一结果或把旧证据重新包装不能累计次数。暂停、版本变化或任一硬门失败后，旧确认计数作废并从影子观察重新累计。

健康分只用于同一资格层内的排序和权重调整。即使健康分很高，只要任一硬门槛、新鲜度或证据确认门禁失败，就没有模拟资金资格。

### 4.4 市场状态路由

每日市场状态是资金入口的上层开关，不是排名后的展示标签。每个策略版本必须冻结四种权威状态（趋势、宽幅震荡、风险下降、极端风险）的完整适配系数、路由策略版本和市场状态配置哈希；历史清单中未冻结路由契约的旧版本必须按“未配置、失败关闭”处理，不能推断默认适配。

治理运行按当天权威市场状态为每个精确策略版本生成可复算的 `router_decision_hash`。组合路由必须由全部精确成员版本的路由共同决定；任一成员不适配、版本不一致或路由哈希缺失时，组合不得授资。当前资金竞争合同固定为 `strategy_capital_competition.v5`：单策略和组合不再先分类型，也不再各自预占 50% 风险预算；全部合格对象按 `扣费后日频 NAV 健康分 × 市场匹配度` 进入同一质量队列，先按展开后的成员袖套做互斥贪心准入，重叠对象只允许质量更高者保留，再在全部入选对象之间按同一质量值和 1bp 最大余数法分配风险预算。相同质量时单策略先于组合、之后按稳定键排序，因此弱组合不能仅凭对象类型挤掉更强成员；相关性、股票重合、袖套数、单票、行业、波动率和预期损失上限仍全部失败关闭。候选集合、分配快照和最终决定三层规范哈希都包含 v5 版本并由健康检查独立重放。旧 v4 canonical 只在运行交易日和完成时间均早于 `2026-08-25`、运行 build 与当前 build 不同且数据库尚未出现任何已完成 v5 canonical 时允许只读重放；当前 build、晚重建或 v5 出现后的 v4 一律拒绝，禁止合同回退。模拟资金分配还必须绑定目标版本、盈利门槛哈希、市场状态、适配分、路由决定哈希、中文生命周期、生命周期倍率和竞争前基础权重，并受当前市场状态的总风险上限约束。竞争后再对“正常运行”乘 1.00、“降权运行”乘 0.50，按 1bp 银行家舍入；折扣资金和风险上限外资金全部留在现金，禁止重新归一化把风险加给其他对象。组合不能只持久化一个平均倍率：每次分配必须输出并仅追加持久化精确 `member_sleeves`，逐成员记录策略版本、配置权重、base bp、成员/组合状态倍率、effective bp、现金折扣和逐行哈希；成员 base bp 等于组合 base bp，成员 effective bp 等于组合最终权重，effective 与折扣之和也必须逐 1bp 守恒。下游只认逐成员 `effective_weight_pct`，不得用组合表面权重绕过成员降权。策略状态仍可保持“正常运行”，但当前市场不适配时本轮权重必须为零；市场路由不能篡改长期盈利证据，也不能绕过盈利硬门槛。

## 5. 两类竞技排名

### 5.1 单策略竞技场

单策略按生命周期赛道、60 日硬门槛、健康分和稳定性排序，同时展示 20/60/120 日指标、版本、样本、回撤、成本压力、准入理由和恢复条件。

单策略同时提供两张证据口径严格隔离的榜单：

- “成交实证榜”只使用内部模拟实际成交、实际费用、现金事件和逐日净值形成的 20/60/120 日证据；它用于展示执行后的真实模拟表现，并且只有该口径能够参与生命周期盈利门槛和模拟资金资格判断。
- “客户端声明信号榜”只使用经双人结构复核的样本外 Walk-Forward 提交，用来比较客户端声明的信号和版本选择质量；其来源未与权威行情逐行认证，固定为研究用途，`source_authority=CLIENT_DECLARED_UNATTESTED`、`funding_authority=false`、`real_order_authority=false`，不能直接授予模拟资金或真实交易权限。

两个策略同日命中同一股票但共享模拟账户容量时，系统不得给未成交策略伪造成交。没有实际执行的客户端声明信号可以进入研究榜，但不会取得成交实证收益；页面必须分别显示两榜的可比窗口、分数和名次，禁止混成一个似乎已经成交或已认证的总榜。

排名只表示在相同证据口径下的相对比较，不代表绝对盈利能力。未通过硬门槛的策略可以在观察赛道排名，但不能因排名靠前获得模拟资金。

### 5.2 组合策略竞技场

组合排名除成员状态外，还必须纳入按冻结配方从成员已验证事实链复算的逐日虚拟净值所计算出的扣费后净期望、利润因子、最大回撤、成员每日收益的成对相关性、股票重合度、行业集中度，以及组合版本自己的 Walk-Forward 选择验证。相关性只能使用日期对齐的共同日收益计算，并达到组合版本冻结的最少观测数；股票和行业集中度必须从底层持仓/候选暴露重算，不能信任成员自报标签。组合使用与单策略相同的生命周期规则，并存在可实际到达的自动升级、降权、暂停和恢复路径。任一成员的检查点未进入本轮资金预算、配方哈希未进入 canonical 清单/健康快照，或详情复算不能得到同一配方哈希时，组合模拟权重必须为零。

只有组合自身和全部必要成员均通过门槛时，组合才可参与模拟分配；否则继续影子验证。没有合格组合时，可以评估合格单策略，但不得为了填排名或凑仓位强制选取对象。

页面中的单策略与组合榜均必须逐窗显示 20/60/120 日成熟交易数、组合覆盖、扣费后净期望、利润因子和窗口门槛结果；不能只显示 60 日主指标后用一句“多窗口通过”代替逐窗证据。组合榜还要直接显示最高成员相关性、最高个股重叠和主要行业权重，票池要同时显示每只股票的行业与主导策略，便于比较不同策略及组合的行业侧重。

## 6. 三层票池

| 票池 | 含义 | 进入条件 |
|---|---|---|
| 观察池 | 展示研究候选和历史复核对象 | 可以包含数据不足或仍在影子验证的对象，但必须显示阻断理由和证据日期 |
| 等待确认池 | 信号已有研究价值，等待价格、数据或门禁确认 | 证据满足基本新鲜度，不存在不可恢复的硬阻断，仍不得视为模拟买入 |
| 模拟可交易池 | 允许参与本轮模拟资金评估的候选 | 当前数据新鲜且已确认、全局门禁允许、精确策略版本具有资金资格、盈利硬门槛通过、无阻断理由 |

“模拟可交易池”允许为空。系统不得为了数量、排名或仓位利用率强制产生候选；页面不得把观察、等待确认或陈旧候选描述成可交易对象。

## 7. 每日治理闭环

`tools/run_strategy_governance_daily.py` 在底层候选快照完成并通过新鲜度校验后执行。默认生产调度由 `tools/add_strategy_governance_task.py` 安装，于 22:35 运行。默认目标不是“数据库里碰巧最新的一天”，而是交易日历给出的最近已收盘权威交易日；18:00 前按尚未结束的交易日回退，周末和节假日按交易日历回退。

每日更新是每日重算市场路由、证据新鲜度、策略健康、生命周期资格、票池和模拟权重，不是覆盖不可变策略公式。信号逻辑、参数、成本模型或组合成员发生实质变化时必须随时注册新版本，从影子观察重新验证。为保证票池完成证明，治理必须读取目标交易日的全部底层股票候选，且 `source_row_count` 必须精确等于 `loaded_row_count`；旧接口中的 `limit` 仅为兼容参数，不能截断权威输入。策略、组合和股票源都不得因该参数被静默截断。每日治理还必须在计算组合行业证据前完成当日行业历史的前瞻冻结；冻结失败时整轮阻断并保持现金。

策略数量不设业务上限时，影子模拟容量仍必须受风控上限约束。系统按权威交易日历的已开市会话序号和稳定策略版本顺序推进容量游标，再按候选序号轮转；容量不足只记为“容量顺延”，风控拒绝单独记账且不消耗容量。仅在策略集合稳定、每天正常运行且每个策略至少有一条可执行候选的前提下，页面才能展示按 `ceil(策略数/每轮最大模拟订单数)` 计算的条件等待上限；该上限只保证获得一次容量评估机会，不保证风控通过、订单接受或产生收益。

动态注册表、候选运行回执和前向证据必须采用有界全量扫描与批量查询，禁止每个策略单独查询形成 N+1。生产验收以不少于 750 个已注册策略的固定查询次数回归证明“策略数增加不会被旧 `limit` 截断，也不会让数据库往返次数线性增长”；单轮模拟下单与扫描上限只限制执行容量，不限制策略发现、注册、排名或审计数量。

行业历史的权威含义固定为目标交易日当时可见的板块成分归属快照，并按精确日期全量回放；它不等同于行业热度、资金流、轮动强弱、估值或行业收益历史。后述数据可以作为独立特征或展示数据，但不能冒充历史成分关系。若目标日期没有通过来源、完整覆盖、行数、分组计数、采集时间和快照哈希校验的成分事实，禁止用最近日期或当前覆盖表回填。

行业数据按用途分层，页面和接口必须显示来源与可用性，禁止混用：

| 数据层 | 当前来源 | 允许用途 | 失败边界 |
|---|---|---|---|
| 精确日期成分归属 | `st_strategy_industry_history` 对 QMT 快照的只追加复刻 | 行业集中度、策略行业暴露、组合约束和动态影子风控的硬证据 | 缺失、重复、截止时间越界或哈希漂移时阻断治理并保持现金 |
| 日级行业/概念热度与涨跌 | `st_hot_concept_ths_daily`，按来源和 `plate_type` 区分同花顺与东财 | 研究特征、轮动观察和页面展示 | 只能标记为来源特定的热度/变化数据；陈旧或缺失时降级，不得代替成分归属或成交实证 |
| 基于 QMT 个股行情聚合的行业强弱 | 当日或历史成员股票的认证行情聚合 | 独立研究特征，且必须冻结成员集合、交易日和聚合协议 | 不能称为官方板块指数；成员或行情认证不完整时输出数据不可用 |
| 原生板块指数实时、分钟和历史行情 | 仅接受完成代码识别、合约和行情认证的 QMT `.BKZS` 数据 | 认证完成后才可新增为独立特征 | 未认证前保持显式缺口，禁止用基准 1000 的合成曲线冒充官方指数价格 |

权威交易日或对应输入未就绪时，脚本必须只输出一个结构化对象并以退出码 2 结束：`status=blocked`、非空中文理由、权威目标日、实际输入日、真实下单权限关闭。每日脚本在输出前必须先自校验，调度器再用同一份规范契约复核所有“完成”“未到期”和“阻断”结果，包括退出码、日期、运行身份、资金 100% 守恒以及任意嵌套层级的真实下单权限；不能把进程退出码 0 单独视为治理成功。只有完全符合契约的退出码 2 才记录为“阻断”；额外日志、字段缺失、日期无效、退出码伪造、资金不守恒或真实下单权限非关闭一律记为失败。

单次闭环必须：

1. 获取目标交易日的单写者锁，确定同日规范版本号和幂等决定哈希，避免页面双击、补跑和调度并发同时产生两套规范事实。
2. 校验底层行情、候选、市场状态和新增证据的新鲜度、确认状态及版本绑定；失败则阻断本轮并保持现金。
3. 冻结本轮策略与组合版本清单，计算 20/60/120 日独立指标和盈利硬门槛。
4. 生成单策略与组合策略竞技排名；组合必须使用自身证据，不能只复制成员结论。
5. 按状态机更新升级、降权、暂停、恢复或淘汰，并写入具体中文理由和证据引用。
6. 生成观察池、等待确认池和模拟可交易池；任一全局数据门禁失败时，模拟可交易池必须为空。
7. 按市场状态、硬门槛、健康分和集中度分配模拟权重；无合格对象时现金权重为 100%。
8. 在同一数据库事务中写入生命周期、审计、健康快照、三层票池、模拟分配和运行汇总；所有明细成功后才能把运行标记为 `COMPLETED`。

任一步失败都必须回滚本轮状态变化，禁止留下“生命周期已改变但审计缺失”或“运行已完成但明细残缺”的记录。失败、阻断和部分结果不能被调度器或健康检查解释为成功。

### 7.1 同日重算与规范版本

同一交易日可能因权威输入更正而需要合法重算，运行表必须同时保留审计历史和唯一当前事实：

- 输入哈希、路由快照哈希和决定哈希完全相同的重试是幂等回放，返回现有规范运行，不新增第二份事实。
- 权威输入确实变化时，新运行使用递增的 `run_revision`，通过 `supersedes_run_uid` 指向被替代运行，并在同一事务内把旧运行标记为非规范、把新运行标记为 `is_canonical=1`；旧运行及其审计不可删除或覆盖。
- 任一交易日任何时刻只能有一条规范 `COMPLETED` 运行。健康检查、页面默认展示、票池和分配验收只读取最新规范版本；历史页面应能查看全部修订和替代关系。
- 并发修订仍受同一交易日的单写者锁保护。新修订任何步骤失败时，旧规范运行继续有效，禁止出现没有规范运行或两条规范运行的中间状态。

## 8. 理由与审计

以下动作必须写入仅追加审计：策略或组合注册、版本变更、证据提交、证据确认或拒绝、自动升级或降权、人工暂停、自动恢复到影子、淘汰、每日运行和失败阻断。

每条审计至少包含：

- 认证系统提供的真实操作人，不能信任客户端自报的 `operator`
- 对象类型、稳定标识、精确版本和版本哈希
- 变化前后状态、中文理由、触发方式和发生时间
- 关联运行编号、目标交易日、输入证据哈希和结果哈希

页面必须准确区分“版本注册”“盈利门槛自动判断”“人工治理”“证据确认”和“运行阻断”，不得把所有非自动事件笼统显示为人工操作。

## 9. API 边界

- `GET /api/strategy-center/governance`：只读取最新 `is_canonical=1` 的完整不可变持久结果；除校验 `result_hash` 外，还必须独立重算路由、票池、分配、成员袖套、生命周期计划和最终决定哈希，并递归确认真实下单权限始终关闭。返回 `result_mode=CANONICAL_PERSISTED`；默认 GET 不实时重算。读取请求不得现场建表、播种或改变生命周期。
- `GET /api/strategy-center/governance/preview`：明确请求一次 `result_mode=PREVIEW_REALTIME`、`is_canonical=false` 的研究诊断重算，不能替代默认 canonical 结果。
- `GET /api/strategy-center/governance/adapter-capabilities`：读取已部署适配器、精确制品 SHA、可识别 evaluator types 和封印状态，不授予资金资格。
- `GET /api/strategy-center/governance/history`：读取轻量的证据、运行和 append-only 动态适配器运行回执摘要；生命周期与操作审计默认不内联原始 JSON。
- `GET /api/strategy-center/governance/history/{lifecycle|audit}`：独立分页读取淘汰、恢复及其他治理理由；游标同时绑定分区、筛选、页大小、修订、`(timestamp, stable_id)` 高水位和页哈希，同一时间的记录不得跳过。
- `GET /api/strategy-center/metrics/{evidence_id}`：读取一份逐笔验证产物及服务端重算结果，供复核人检查。
- `POST /api/strategy-center/registry`：注册新策略或不可覆盖的新版本。
- `POST /api/strategy-center/combinations`：注册新组合或不可覆盖的组合版本。
- `POST /api/strategy-center/metrics`：提交待校验的外部独立证据；提交成功不等于证据已确认或已取得资金资格。
- `POST /api/strategy-center/metrics/{evidence_id}/review`：由不同认证身份确认或驳回证据，复核时再次重算完整产物。
- `POST /api/strategy-center/strategies/{key}/lifecycle`：人工暂停、把正式策略转回影子研究或淘汰；不能人工恢复已暂停版本。
- `POST /api/strategy-center/combinations/{key}/lifecycle`：对组合执行相同的人工治理动作。
- `POST /api/strategy-center/governance/run`：针对最新已确认交易日执行并原子持久化一次完整治理闭环。

治理运行请求中的 `limit` 是保留的兼容参数，不是策略数量或票池读取上限。权威候选必须全量读取，并以精确源行数、加载行数和明细哈希证明完成；动态策略、组合注册表和底层票池均不得因该参数被截断。

所有写接口必须经过生产认证和同源保护，操作人由服务端身份生成，并具有幂等或冲突语义。职责必须分离：`ADMIN` 负责策略/组合注册、启停、生命周期治理、手工运行和外部证据提交；`EVIDENCE_REVIEWER` 只能独立确认或驳回证据，不能注册策略、提交证据或执行治理；旧管理令牌不能参与上述治理写操作。管理员可以通过 `POST /api/auth/users` 创建独立复核账号，但复核账号不能创建其他账号。参数错误、版本冲突、实体不存在、角色不符和服务端失败应使用相应的非 2xx HTTP 状态，不得用 HTTP 200 掩盖失败。

规范治理总览只返回单策略榜和组合榜各自的首 50 行。后续排名通过独立 GET 分页接口读取，稳定游标和 `page_hash` 必须同时绑定 `run_uid`、`canonical_result_hash`、对象类型、搜索词和偏移量；canonical 修订变化时返回冲突并要求刷新，禁止跨修订拼页。完整 canonical 结果仍在服务端按原始 `result_hash` 校验，分页不会改变排名或规范结果。20/60/120 日详情同样按需分页，不得把日频事实数组重复内联到排名、三窗健康快照和 canonical 结果中。

资金详情只能在规范检查点、canonical 锚、共享审计锚和规范化日频事实链全部复算通过后读取；每页最多 50 行，游标绑定检查点、链哈希、事实集合哈希、窗口、序列和页大小。检查点 `state` 不保存也不提供 `rolling_history`，日频收益、实际费用、净值、个股风险敞口、平仓集合和事实成员必须来自同一份已验证规范事实链；当前未平持仓只能来自检查点状态哈希。

外部版本选择证据的默认详情只返回逐笔交易数、权益点数、Walk-Forward 分段数、训练样本数及相应哈希，不返回完整 `artifact_manifest`。逐笔交易、权益曲线、分段索引和单段训练集分别通过绑定 `evidence_id` 与 `artifact_hash` 的独立 GET 接口读取，每页最多 100 行；分段列表不内联最多十万条的训练集。旧详情接口不得再把几十 MB 的证据数组一次发送到浏览器。

外部证据的逐行数量上限继续保留，同时增加总容量硬合同：规范化 `artifact_manifest` UTF-8 JSON 最大 48 MiB，两个证据 POST 端点的完整请求体最大 52 MiB。请求体在 FastAPI/Pydantic 物化 JSON 前按流累计，伪造或缺失 `Content-Length` 不能绕过；超限返回 HTTP 413，不进入重放、数据库事务或审计入库。

## 10. 新增策略流程

1. 选择未占用的稳定 `strategy_key`，填写中文名称、类别、负责人、适用市场、信号逻辑、风险条件和失效条件。
2. 提交唯一版本、评估器配置、参数、成本模型和可复现代码或制品哈希；服务端规范化后生成不可变 `version_hash`。
3. 注册成功后固定进入“影子观察”。注册元数据本身不能生成资金资格。
4. 部署并验证该精确版本的信号适配器，确保候选、逐笔结果和审计都携带相同版本身份。
5. 在版本冻结后启动内部模拟执行，持续形成含实际费用、现金、重叠持仓和每日盯市的版本绑定组合账本；这是后续生命周期和授资判断的唯一收益来源。
6. 可选提交带标签声明成熟边界、purge/embargo、训练/测试集哈希的外部 v3 Walk-Forward 客户端研究声明；系统只校验格式、范围、日期、版本、隔离协议和提交内容哈希，并由不同认证账号做结构复核。它最多帮助挑战者晋级为无资金影子版本，不证明权威数据来源，也不能影响资金资格。
7. 每日治理只按内部资金事实使用 20/60/120 日窗口评估；内部账本不足时继续影子观察，内部证据失效时降权或暂停，全部内部门槛通过后才可自动进入正常或降权运行。外部声明缺失、好坏或新鲜度均不改变这条资金状态机。
8. 参数、逻辑、成员或成本口径发生实质变化时必须注册新版本，并重新执行上述流程。

新增组合遵循同一流程，同时必须冻结成员精确版本、权重和相关性/股票重合/行业集中度约束，并从成员权威事实链生成组合自己的内部逐日虚拟净值。组合可以另存客户端研究声明，但不要求它作为资金门槛。

## 11. 生产验收

运行 `tools/check_strategy_governance_health.py` 前必须完成数据库迁移和调度安装。验收必须失败关闭，并至少同时证明：

### 11.1 数据库迁移权限与故障边界

生产 MySQL 位于 Windows 主机，Linux 应用端经现有受控隧道以 TCP+TLS 连接，禁止再假设本机 MySQL socket、named pipe 或 Linux root 数据库身份。TLS CA 固定为 `/etc/probiga/mysql84-ca.pem`；必须与运行配置指向同一个普通文件，由 root 所有，不是符号链接，且文件及所有父目录不可由组或其他用户写入。发布使用三个彼此不同且无可激活角色的账号：`probiga_trigger_admin@127.0.0.1` 全局权限精确为 `SYSTEM_VARIABLES_ADMIN, SHOW_ROUTINE`，前者只用于切换 `log_bin_trust_function_creators`，后者只用于完整只读 routine 库存证明；`probiga_migrator@127.0.0.1` 只允许 `probiga.*` 的迁移权限；运行账号继续由 root-owned systemd EnvironmentFile 提供，全局只允许 `USAGE` 并强制 `REQUIRE SSL`。为避免现网旧授权在无停机发布的 preflight 阶段自锁，第一阶段只接受两个精确 schema 合同：目标合同 `TARGET_LEAST_PRIVILEGE` 为 `biga.* = SELECT`、`probiga.* = SELECT, INSERT, UPDATE, DELETE, CREATE TEMPORARY TABLES`、`probiga_qmt_history.* = SELECT`；受控兼容合同 `LEGACY_DDL_COMPATIBILITY` 仅允许在上述基础上完整保留现有五项 `CREATE, ALTER, DROP, INDEX, REFERENCES`，少一项、多一项或任何其他授权都阻断。发布证据必须如实返回 `observed_contract` 和实际 `persistent_ddl_privileges`，兼容态不得显示成已完成最小权限。生产运行代码已经禁止所有持久 DDL，结构迁移只能由围栏内迁移账号执行；后续在独立维护窗对运行账号 `REVOKE` 这五项后，同一门禁自动识别为目标合同。`TRIGGER` 始终不在两个运行合同内。还必须拒绝 `ALL PRIVILEGES`、`EVENT`、`CREATE/ALTER ROUTINE`、`EXECUTE`、`CREATE/SHOW VIEW`、`LOCK TABLES`、任何全局管理权限、`GRANT OPTION`、`PROXY`、角色以及表或列级旁路授权；三个 schema 中的 `SQL SECURITY DEFINER` routine 库存必须由具有完整可见性的独立管理员连接证明为零，运行与迁移账号仅补充证明自身未拥有此类 routine，不得用其受限视图冒充完整库存。

管理与迁移凭据分别固定在 `/etc/probiga/mysql-trigger-admin.ini` 和 `/etc/probiga/mysql-migrator.ini`，必须为非符号链接、root:root、`0600`，父目录不可由组或其他用户写入；密码不得出现在命令行、项目环境变量、代码、日志、异常或部署回执中。这两个文件和上述精确运行权限必须在发布前的受控账号预置维护中完成；普通部署不创建账号、不传递密码、不放宽权限，缺少任一条件立即失败关闭。本次结构维护也不改变“生产交易激活仍为关闭”和“禁止自动真实下单”的边界。

preflight 必须在旧服务仍正常运行时完成，并保持严格只读：逐项核验 Oracle MySQL 8.4.11、固定 server UUID/hostname/端口、TLS cipher、`log_bin=ON`、`binlog_format=ROW`、全局 trust 为 `OFF`、三个精确身份及权限范围、全部已登记 V3 的 checksum/statement count/物理结构、精确待迁移集合、QMT/治理表的全有或全无状态，以及所有已存在触发器的正文、时机、事件、目标表、`DEFINER`、SQL mode、字符集和排序规则。允许迁移的旧例外只限两条已审计的 `root@localhost` 交易账户保护触发器及其精确旧 SQL mode；任一部分匹配、额外触发器、跨库授权或未来迁移提前出现都必须阻断。

cutover 顺序固定为：停止并禁用 AI worker 及 timer、scheduler 和 API；通过数据库 writer fence；为四个 systemd writer unit 安装固定 `ConditionPathExists` 保护并持久写入 root 所有的 guard v2，同时记录四个 unit 在 cutover 前的 load/active/unit-file 精确状态；用迁移账号在 trust=`OFF` 下完成表、列、索引和数据回填；只有确实缺失的冻结 `CREATE TRIGGER` 才允许由管理账号短暂把 trust 切到 `ON`，且每创建一条后立即恢复 `OFF`，通过原管理连接、新管理连接和独立运行连接三重读回验证。运行账号在所有层级都没有 `TRIGGER`、routine 或 event 创建权限，因此 trust 窗口不会为运行凭据增加新能力。触发器必须最终统一为 `probiga_migrator@127.0.0.1` DEFINER 和冻结的会话元数据。完全幂等、没有触发器差异的重跑不得打开 trust 窗口。

结构完成后还必须单独执行一次 `recover` 验证、完成 QMT 历史协议升级及严格结构/数据检查，再由普通运行账号使用 `--schema-prepared` 做只读计划和调度安装。生产运行路径中的治理初始化只能只读验证已准备结构，不得执行永久 `CREATE`、任何 `ALTER`、触发器 DDL 或结构回填；QMT 历史认证为处理大批量数据可在当前数据库会话中执行 `CREATE TEMPORARY TABLE` / `DROP TEMPORARY TABLE`，临时表不得跨会话留存，除此之外的 DDL 一律由 SQL guard 拒绝。

生产发布必须精确核验 68 条冻结触发器，分组固定为：治理 40 条、PIT 数据保护 6 条、QMT 完成运行认证 6 条、QMT 不可变参考数据 10 条、QMT 历史覆盖认证 4 条、调度任务历史/发布回执 2 条。不得只验证治理 40 条便宣称结构就绪，也不得用“应用层只写”或能被重算的行哈希代替任一组数据库保护。治理 40 条中，38 条属于治理行保护，另 2 条属于指标复核状态机。38 条包括原有版本、生命周期、审计、运行和六类快照/回执的 22 条，四张动态影子账本的 8 条，治理迁移标记的 2 条，两张资金事实/检查点表的 4 条，以及策略/组合当前注册表各 1 条删除拒绝触发器。指标表的更新触发器只允许核心字段完全冻结且由不同复核人执行一次 `PENDING → CONFIRMED/REJECTED`，删除触发器无条件拒绝。策略注册表和组合注册表仍需受控更新名称、启停、当前版本和状态，但禁止删除；每次健康检查必须从不可变生命周期事件逐条复算当前版本、状态和理由，验证合法前后状态、版本注册重置和同版本 `RETIRED` 终态，并与两个当前注册表精确相等。发布、恢复和每日健康检查都必须按六个分组精确核验全部 68 个名称、正文、时机、事件、目标表、`DEFINER`、SQL mode、客户端字符集、连接排序规则和数据库排序规则；少一条、多一条、改名、跨组替代或任一元数据漂移都失败关闭。治理组中冻结的 38 条治理保护合同哈希为 `1fcde61ce5a5ea0cc16f1910d94da431d044c667383fafd2224217709f555943`，2 条指标复核合同哈希为 `0dbaa644427139c472bab0c3f719d78bd292bb6a7726a0f0ef195adc2e37fa84`；68 条非 V3 发布触发器的冻结源合同哈希为 `4a59e6364edc9191dc08131e1806fe58ddf5231b41a4bd7627606d024a6c5175`。代码、迁移、健康页和部署解析器必须使用同一冻结清单与合同。完全幂等且 68 条均无变化时不得打开 trust 窗口。

QMT 认证表、治理表及其全部字符列的冻结排序规则均为精确的 `utf8mb4_unicode_ci`，不能把其他 `utf8mb4_*` 视为等价。首次上线前必须只读盘点生产实际表/字段排序规则；任一不一致都属于发布前置阻断，只能另行设计、评审并在写入方已围栏的维护窗口执行受控转换，普通部署与历史认证任务不得自行 `CONVERT` 或悄悄修复。

持久 guard 只能在 trust 三重确认为 `OFF`、全部迁移为 `exists`、QMT 与治理表完整、触发器无旧元数据且严格结构验证通过后清除。任一异常、信号中断、DROP 后 CREATE 失败、身份或权限漂移都保持 guard 及四个 systemd 条件，回滚只能恢复旧发布文件并保持所有 writer 停止/禁用，写入 `BLOCKED_DATABASE_GUARDS` 回执。SIGKILL 或 Linux 主机丢失不能执行 Python `finally`，因此后续只能进入显式 root 恢复模式：先修复并验证固定 drop-in、writer 和 guard 未被绕过，再用 guard 记录的不可变发布依次执行 admin-first `recover`、新一轮 L4 writer fence、`resume --writers-fenced`、再次 `recover` 和严格只读 preflight。`resume` 只能修复两条冻结 legacy trigger 中“完全缺失”的项，改名、正文或元数据漂移仍然拒绝，并必须返回 candidate/repaired/post-validation 证据。上述全部通过后才可清 guard；随后必须精确恢复 guard v2 记录的原 unit 状态并验证服务健康。清闩或状态恢复失败时必须立即按同一发布 SHA 重新上闩，停止并禁用全部 writer 及 activation unit；任何证据不全继续停机，禁止手工跳过验证后直接启动服务。

QMT 旧协议首次绑定不得修改原运行行、不得伪造 V2 universe manifest，也不得计入授资证据。生产只允许将精确 11 条已完成旧行绑定为 `LEGACY_V1_INELIGIBLE_NO_UNIVERSE_MANIFEST`，其排序全行聚合 SHA-256 必须为 `fc8328550615413445edf1055b3b88d70fa8b37e45ee331f682cf8f654779b54`。首次追加 marker 前及之后的任何行数、原始容差 JSON、计数、日期、provider 或聚合哈希漂移都必须阻断。新历史只能由当前 V2 协议和真实逐日 manifest 产生。

发布还有一条不可跳过的安全前置：代码库当前版本及历史中出现过的数据库/远程密码必须在独立维护窗完成轮换；已验证 `probiga-deploy` 公钥和受限 root broker 后，必须关闭 SSH root 登录、密码认证和交互式认证，并用新独立连接复验。源码中的明文删除不等于历史凭据已轮换；两项外部状态未完成前禁止生产上线。
