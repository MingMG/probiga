# 稳定获取数据：全链路审查与实施方案

日期：2026-09-05。基线：`6c503a68ca1546b6705e17dd7b4f61986533b30c`。

**状态：部分修复在隔离分支通过测试；生产未更新，不能宣称已恢复稳定。发布失败恢复协议、历史证据消费以及数据源授权仍有明确未完成项。**

## 1. 决策

采用“采集独立推进 + 同口径数据源切换 + 自动补缺 + 可恢复发布”的方案。复用当前数据库、任务调度、分区修复和写入围栏，不引入消息队列、另一个调度平台或全面重写。

稳定不是要求外部接口永不失败，而是：失败可被发现、能按有界策略重试或切换、恢复后能补齐、不损坏已有数据、不把缺失当作成功。无法得到的必需证据必须明确阻断相关结果，不能用旧值、零值或不同含义的数据冒充。

| 候选方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 保留原链路，只增加重试/延长超时 | 代码少，短暂网络波动有时能恢复 | 不解决循环依赖、永久不可重试、发布停采；可能造成请求风暴 | 不作为主方案 |
| 只更换一个数据接口 | 可绕开单个坏接口 | 新接口也可能断；日期、股票范围、字段定义可能不同；内部停采仍存在 | 必要时替换源，但不足以解决全链路 |
| 本方案：拆清职责，复用已有机制 | 直接覆盖已复现根因，保留审计/幂等/安全，改动集中 | 需要补正式发布恢复协议和契约测试；某些历史数据需要付费授权 | **推荐且有必要** |
| 全新数据平台/多套调度/全面微服务化 | 最终扩展空间较大 | 迁移和维护成本高，当前故障面扩大，不能更快恢复 | 当前不采用 |

## 3. 目标流程与边界

```text
权威交易日历与股票目录
       ↓
各数据集独立采集 → 暂存/校验 → 原子发布完整分区
       ↑                            ↓
有界重试 / 合格备用源 ← 缺口扫描 ← 分区水位和来源
                                    ↓
                     分析 / 策略 / 页面只消费已验证输入

代码发布：准备候选 → 授权停写 → 切换 → 提交
                                      ↘ 失败：证明安全后恢复原采集
```

1. 原始采集按最新闭市交易日推进，不因旧策略失败停止下一天采集。近期修复负责漏日；观察时间数据和历史事实分别处理。
2. 原始采集失败只改变自己的 attempt/history，不篡改策略签名终态；保留锁、租约、fencing 和真实 build 来源。
3. 下游依赖以上游完成为依据，不以某个固定分钟到了就假设有数据。资金流必须等当日日线股票范围就绪。
4. 分区完整性按“日期 × 必需股票键 × 必需字段”计算。停牌、未上市、源不支持不是网络失败，必须有清楚状态；不制造对应数值。
5. 近期缺口扫描独立于策略成功状态。使用现有状态文件与幂等发布；默认修复窗口之外的停机要显式扩大回看范围，不能声称默认 5 日会补完任意长停机。
6. 新源先旁路比较，不直接替换正式因子。记录 provider、观察时间、适用日期、单位、定义版本和修订信息。

## 4. 哪些源保留、哪些需要替换

| 数据 | 近期选择 | 更换条件和限制 |
| --- | --- | --- |
| 交易日历 | 交易所公告生成并提前更新全年日历；统一供采集/补数/分析使用 | 日历将到期须提前告警；不能以简单工作日规则长期替代法定休市 |
| 日线/成交量 | 保留已接入且能验证的 QMT 正式采集；单独解决运行条件 | 如果无人值守运行不能达标，评估独立历史行情 API；先验证复权、成交量单位、停牌和股票目录，不直接替换为当前网页快照 |
| 日资金流 | 默认同一供应商历史 API 的不同传输路径；接入每日修复 | 东方财富与百度“大单”等定义未证明等价，禁止静默混填；显式选择其他定义时必须版本化并重新验证依赖因子 |
| 历史涨跌停 | 对现有 MyQuant 做廉价真实字段能力探针；失败立即报告，不先全市场计算 | 候选为迅投历史 stoppricedata 或 Tushare stk_limit；需确认现有授权和真实样本。不能由当日 f51 或按涨幅推算替代历史上限证据 |
| 分钟数据 | 独立产品、独立时段覆盖检查 | 分钟不完整不得冒充全天；不应阻断不消费分钟数据的日线采集 |
| 公告/财务/行业 | 区分当时已知的观察记录和可依法重建的历史事实 | 今天抓到不等于历史决策时已知。无法还原的 PIT 事实明确缺失，不能为恢复旧策略改时间戳 |

替代源证据：

- [迅投官方股票数据字典](https://dict.thinktrader.net/dictionary/stock.html)提供历史涨跌停价格能力，属于扩展权限范围；本机独立 xtquant 探针未能连接，尚未验证账户可用性。
- [Tushare 官方每日涨跌停价格接口](https://tushare.pro/document/2?doc_id=183)提供按日期的 pre_close、up_limit、down_limit，需要相应积分权限。它是候选，不是已开通或已验证的备用源；停牌等其他必需字段仍须补足。

**采购前置条件：**确认用户现有授权、覆盖历史范围、限流额度、预算和许可。未经确认不购买。专业/付费 API 也不天然保证零故障，必须验证授权、接口能力、服务承诺及故障恢复。

## 5. 执行顺序、交付物与必要性

### A. 采集不被策略拖停：隔离分支已实现

- 明确 7 类原始采集，使用独立最新闭市目标。
- 保留策略不可重试终态和签名；原始任务仍受租约/围栏约束。
- 近期修复移出策略门禁，补资金流→日线依赖。
- 延期不再覆盖首个真实错误。

优点：直接解除两处已确认内部阻塞，无新平台。代价：修复历史数据不自动等于历史策略拥有正式证据，必须保持边界。必要性：必须。

### B. 同口径获取、补数与监测：隔离分支已实现并通过相关回归

- 开放日没有日线先决条件时，补数不得报告 expected=0/unresolved=0 的成功。
- 默认不静默跨供应商混因子，保留显式来源选择并报告来源分布。
- 自动修复接通历史日资金流路径，数据源失效不能破坏既有完整分区。
- 涨停源先廉价探测能力，再做重型预分析；探针永不充当完整历史证据。
- 复用 `tools/data_quality_check.py --acquisition` 汇总日历、两端心跳、近 21 个交易日整日缺口、目标日资金流键覆盖。所有查询只读，独立于策略结果。

**监测能力不夸大：**该 CLI 是有限运行观察，不覆盖逐股历史全量完整性、完整分钟时段、全部公告/财务/行业证据或正式发布授权。PASS 不是全链路稳定验收。底层正式分区验证和后续业务验收仍必须完成。

### C. 发布失败恢复：尚未实现，生产发布阻断

详见 [v2 最小恢复协议](qmt_edge_release_recovery_protocol_v2.md)。复用受保护账本、root broker 和数据库锁，增加全局尝试及互斥的 COMMIT/ABORT_RESUME 终态；先兼容 reader/controller，再启用 writer；保留可恢复旧制品。

优点：修复发布之后断电、断网、迁移失败也可能永久停采的根因。代价：需要跨端兼容上线和故障注入，不是简单重启。必要性：必须。不能以预检查或超时删除 hold 替代。

长期将 `app_release_sha` 与 `ingest_release_sha` 分开，以显式兼容合同控制写入资格，保留每条数据的真实构建来源。无需拆仓库；页面单独发布不应启动采集停写事务。

## 6. 稳定性的验收门槛

以下是建议的服务目标，尚非已达到的实绩。具体完成窗口按选定供应商发布时间确定：

- 核心日线/同口径日资金流以收盘后 18:00 为首轮完成目标；若供应商正式 SLA 更晚，明确更新目标，不偷偷把旧日标成今日。
- 默认 60 秒调度心跳，连续 2 分钟无心跳即故障；使用独立运行的现有监测/通知渠道，不由已停止的采集进程自报健康。
- 5/15/30 分钟等有界退避须在实际源限流允许范围内；权限、字段定义不兼容不作无限重试。
- 漏交易日必须列出清单，恢复后从缺口继续。可恢复分区只更新缺失/无效部分，重复执行无重复键、无已完成数据损坏。
- 先用断线、超时、空响应、错误日期、部分股票、权限拒绝、任务被杀、跨日、发布中止等模拟故障证明恢复；再观察至少 5 个实际交易日无人干预运行。测试通过不能替代该生产观察。
- 告警包含数据集、目标日期、缺口数量、首个根因、重试/切源状态；按故障归并，恢复时通知一次，不刷屏。
- **生产放行必须证明：**源有授权、所需窗口完整或显式例外、两端运行正常、发布失败可恢复、分析实际消费链通过。当前这些条件尚未全部成立。
