# 稳定获取数据：全链路审查与实施方案

日期：2026-09-05。基线：`6c503a68ca1546b6705e17dd7b4f61986533b30c`。

**状态（2026-09-06 更新）：新的直接采集入口及资金流整日原子发布已在隔离分支实现，生产未更新，不能宣称已恢复稳定。生产业务表 schema 已只读核对并形成精确迁移；国金完整 QMT 商用授权由用户确认，资金流仍须在真实完整 QMT 内模型完成单股单日 `transactioncount1d` 探针后才能启用。**

## 1. 决策

采用“采集独立推进 + 同口径数据源切换 + 自动补缺 + 可恢复发布”的方案。复用当前数据库、任务调度、分区修复和写入围栏，不引入消息队列、另一个调度平台或全面重写。

稳定不是要求外部接口永不失败，而是：失败可被发现、能按有界策略重试或切换、恢复后能补齐、不损坏已有数据、不把缺失当作成功。无法得到的必需证据必须明确阻断相关结果，不能用旧值、零值或不同含义的数据冒充。

| 候选方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 保留原链路，只增加重试/延长超时 | 代码少，短暂网络波动有时能恢复 | 不解决循环依赖、永久不可重试、发布停采；可能造成请求风暴 | 不作为主方案 |
| 只更换一个数据接口 | 可绕开单个坏接口 | 新接口也可能断；日期、股票范围、字段定义可能不同；内部停采仍存在 | 必要时替换源，但不足以解决全链路 |
| 本方案：拆清职责，复用已有机制 | 直接覆盖已复现根因，保留审计/幂等/安全，改动集中 | 需要补正式发布恢复协议和契约测试；某些历史数据需要付费授权 | **推荐且有必要** |
| 全新数据平台/多套调度/全面微服务化 | 最终扩展空间较大 | 迁移和维护成本高，当前故障面扩大，不能更快恢复 | 当前不采用 |

## 3. 目标流程与边界

```text
权威交易日历与股票目录
       ↓
各数据集独立采集 → 暂存/校验 → 原子发布完整分区
       ↑                            ↓
有界重试 / 合格备用源 ← 缺口扫描 ← 分区水位和来源
                                    ↓
                     分析 / 策略 / 页面只消费已验证输入

代码发布：准备候选 → 授权停写 → 切换 → 提交
                                      ↘ 失败：证明安全后恢复原采集
```

1. 原始采集按最新闭市交易日推进，不因旧策略失败停止下一天采集。近期修复负责漏日；观察时间数据和历史事实分别处理。
2. 原始采集失败只改变自己的 attempt/history，不篡改策略签名终态；保留锁、租约、fencing 和真实 build 来源。
3. 下游依赖以上游完成为依据，不以某个固定分钟到了就假设有数据。资金流必须等当日日线股票范围就绪。
4. 分区完整性按“日期 × 必需股票键 × 必需字段”计算。停牌、未上市、源不支持不是网络失败，必须有清楚状态；不制造对应数值。
5. 近期缺口扫描独立于策略成功状态。使用现有状态文件与幂等发布；默认修复窗口之外的停机要显式扩大回看范围，不能声称默认 5 日会补完任意长停机。
6. 新源先旁路比较，不直接替换正式因子。记录 provider、观察时间、适用日期、单位、定义版本和修订信息。

## 5. 执行顺序、交付物与必要性

### A. 采集不被策略拖停：隔离分支已实现

- 明确 7 类原始采集，使用独立最新闭市目标。
- 保留策略不可重试终态和签名；原始任务仍受租约/围栏约束。
- 近期修复移出策略门禁，补资金流→日线依赖。
- 延期不再覆盖首个真实错误。
- 同一自然日早上补昨日数据成功，不能占用下午新交易日的运行资格；cron 完成判断必须匹配已绑定的交易日，仍不得提前越过该任务的运行时间。

优点：直接解除两处已确认内部阻塞，无新平台。代价：修复历史数据不自动等于历史策略拥有正式证据，必须保持边界。必要性：必须。

### B. 同口径获取、补数与监测：隔离分支已实现并通过相关回归

- 开放日没有日线先决条件时，补数不得报告 expected=0/unresolved=0 的成功。
- 默认不静默跨供应商混因子，保留显式来源选择并报告来源分布。
- 日资金流逐证券结果先 staged 到既有进度行；目标日预期证券全部齐全后，在现有资金流锁内一次事务替换整日并独立回读。中断后只补未 staged 证券，未集齐时不碰旧完整分区。
- 涨停源先廉价探测能力，再做重型预分析；探针永不充当完整历史证据。
- 复用 `tools/data_quality_check.py --acquisition` 汇总日历、两端心跳、近 21 个交易日整日缺口、目标日资金流键覆盖。所有查询只读，独立于策略结果。
- 不新增调度服务。既有 `capital_flow_batch_fast` 任务身份保留为 readiness 兼容点，但执行内容改为只读验证新 QMT 进度和正式业务分区；旧 `capital_flow` 及原批量/补数 writer 退役，不能被 ensure 再启用。

**资金流到消费的边界：**只有整日原子发布并按预期证券键、日期和 `gj_big_qmt_inner` 来源回读成功，readiness 的只读验证才可通过。`staged`、旧 push2 数据或某次任务 exit 0 都不是完成证据。事后补数无法制造早先 cutoff 的财务/公告/行业观察记录，因此旧策略仍可能合法 BLOCKED，不回退最新采集目标或清除已签名终态。

**生产 schema 当前事实：**2026-09-06 已只读核对主库和历史库。现有股票/指数行情、资金流、公告等业务表可复用，两库尚缺进度表。切换前的精确业务迁移仅为：`sm_etf_kline` 五个验证/质量/权限字段改为可空，`si_etf_code` 两个验证/同步字段改为可空，`si_stock_finance` 增加 `source_update_date`，`st_a_list_daily` 增加 `trade_id`，`st_a_list_info` 增加 `trade_id/report_side`。不新增用户、角色、权限框架或服务；只读核对不等于迁移已应用。

**两个执行器不能混淆：**Windows edge 调度器负责正式按日任务，其全局发布 hold 会阻止这些任务；旧 QMT 实时 `run_big_qmt_bridge.py` consumer 则由 `ProBigA Local Live Services` 独立 supervisor 管理，受 `BIG_QMT_BRIDGE_ENABLED` 控制。现行日线链是 edge → `sync_qmt_stock_edge.py` → `sync_qmt_primary(require_bigqmt=True)` → 原生 spool，并不依赖旧 consumer 回执；默认 Linux 实时报价另从东方财富获取。原生 producer 健康但旧 consumer 回执过期，不能直接判定现行日线链故障，也不能为修日线恢复整套旧 supervisor 而引入额外写入者。生产任务 52 `qmt_intraday_realtime` 的脚本名仍为 `sync_qmt_realtime.py`，本轮已把其内部 MiniQMT 路由改为完整 QMT 原生快照；必须验收它自己的任务 history、库内来源及事件时间，不以旧 consumer 回执代替。修改尚未部署。

**历史日线凭据门禁：**已确认凭据文件自身是 protected 私有 DACL、单硬链接且无 reparse；阻断来自父目录额外的 ReadAndExecute 权限，而非密码可读。只将目录规则改为禁止所有非授权写入、删除、改 ACL 和所有权接管；文件的精确私有 DACL 不变，不改生产账户或目录权限。生产只读权限验证现已通过，关联隔离回归 133 项通过；这不表示已写入缺失的 9 月 3 日日线。

**完整 QMT 实时写入：**仅接受原生来源和原生事件时间，120 秒内且同交易日期的数据才计覆盖；沿用原 60% 覆盖门槛。原始零/负价格、负成交量/成交额、非有限数值或缺字段不能经前收替换、归零后变成合格行情。写入复用原命名锁并独立回读；合法较新行情保留，较新但未来时间/坏价格的存量行明确报错，不自动修库。仍标为 `PENDING`，不授予交易资格。

**监测能力不夸大：**该 CLI 是有限运行观察，不覆盖逐股历史全量完整性、完整分钟时段、全部公告/财务/行业证据或正式发布授权。PASS 不是全链路稳定验收。底层正式分区验证和后续业务验收仍必须完成。

### C. 发布失败恢复：两阶段兼容已实现，生产验收待执行

详见 [v2 最小恢复协议](qmt_edge_release_recovery_protocol_v2.md)。复用受保护账本、root broker 和数据库锁，增加全局尝试及互斥的 COMMIT/ABORT_RESUME 终态；先兼容 reader/controller，再启用 writer；保留可恢复旧制品。

恢复只覆盖“切换前、schema 未变、可证明原采集先前运行”的窄边界。现已补首次兼容入口：首个受控发布只安装新 reader/controller，继续使用原 v1 hold 和真实最终 grant；两主机 exact-ready 后再由独立审查提交启用新恢复 context。存在任意受保护 context 后，旧兼容写入口永久拒绝。当前 Windows 正式 edge 任务已停、无对应残留 Python 进程，首阶段属于前向恢复，不假称可自动回滚任意旧故障。真实双机和 MySQL 权限/锁验收仍未完成。

采用既有非阻塞数据发布模式，同时三个成功分支均启动原有数据观察服务：结构、seal、身份、写入围栏和最终授权仍阻断发布；策略/历史数据缺口不阻断采集修复代码安装。它跳过部分全库业务账本审查，必须独立报告，不能以 observer 替代或称完整策略已验收。

优点：修复发布之后断电、断网、迁移失败也可能永久停采的根因。代价：需要跨端兼容上线和故障注入，不是简单重启。必要性：必须。不能以预检查或超时删除 hold 替代。

长期将 `app_release_sha` 与 `ingest_release_sha` 分开，以显式兼容合同控制写入资格，保留每条数据的真实构建来源。无需拆仓库；页面单独发布不应启动采集停写事务。

## 6. 稳定性的验收门槛

以下是建议的服务目标，尚非已达到的实绩。具体完成窗口按选定供应商发布时间确定：

- 核心日线/同口径日资金流以收盘后 18:00 为首轮完成目标；若供应商正式 SLA 更晚，明确更新目标，不偷偷把旧日标成今日。
